# Apparent work: make the spectacle imply a purpose

The screen is a fictional instrument doing something, not an animated sculpture.
The user need not understand its domain or obtain useful information, but should
be able to infer: something arrived, the system considered it, something changed,
and a result came out. Technical plausibility is theatrical; internal continuity
is what makes the performance convincing.

## Design the activity before decorating it

Write one sentence naming the system's supposed job. Then define the objects it
handles, their stages, possible decisions, and visible outputs. Give several
objects persistent short identities so the eye can follow them across views.

| Subject | Work object | Visible process | Consequence |
|---|---|---|---|
| Trading | Order / quote | Compare venues → risk check → route → partial fill | Depth consumed, position updated, settlement receipt |
| Weather | Observation / storm cell | Scan → correlate → classify → forecast | Track branches, confidence changes, warning issued |
| Infrastructure | Request / incident | Queue → allocate → execute → retry | Capacity shifts, queue drains, result appears |
| Research | Source / hypothesis | Retrieve → compare → challenge → synthesize | Evidence links accumulate, competing hypothesis is discarded |
| Alien instrument | Contact / specimen | Acquire → isolate → decode → contain | New structure revealed, translation fragment stored |

These are examples, not a required node graph. A dense trading terminal can imply
work through linked books, tapes, matrices, annotations and logs. Agents and
characters are optional. Actual backend operations are unnecessary.

## Show evidence of activity at several scales

- **Local:** a scanner reveals a feature; rows are compared; a candidate is crossed
  out; a progress trace reaches a boundary; a partial result accumulates.
- **Across views:** the same order ID, color or shape leaves one region and arrives
  elsewhere; its receipt updates a related chart, inventory or queue.
- **Over time:** completed work remains in a short history. Some objects wait,
  fail, retry or take another path. A result changes the next visible state.

Avoid a wall of randomly changing numbers and arbitrary success messages. Derive
the visible artifacts from a small deterministic event/state model. The model can
be invented and simple; the consistency is visible. Logs describe events that
actually occurred in the simulation, not an unrelated ticker of technical words.

## Assign motion a job

For each prominent effect, name its trigger, what it communicates, and what changes
when it finishes. A traveling packet carries an identifiable object. A ring is a
scan window that reveals a feature. An opening assembly exposes a processing
stage. A burst represents a backlog clearing and leaves receipts behind.

Keep atmospheric particles subordinate. If removing the particles leaves no
visible work, fix the process staging. More particles cannot supply purpose.
Do not replace lavish art direction with a plain workflow chart: turn the
fictional process into the machinery, instrumentation and choreography.

## Review the illusion, not just the geometry

Watch a silent 10-second sequence. Can you point to an input, a decision or
transformation, and its consequence? Follow one identity between two views. Inspect
what remains after completion. Introduce one constraint, such as a blocked venue:
does the traffic change route, a queue grow, or an alternate result appear?

It is fine for most details to be cryptic. The broad verbs should be legible.
Synchronized animation alone does not establish cause and effect. A beautiful
hero-only frame is useful art-direction evidence, but cannot pass this work test.
Keep fictional/simulated status visible without undercutting the performance.
